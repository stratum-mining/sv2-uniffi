# C bindings

A C API over the [Stratum V2 Reference Implementation](https://github.com/stratum-mining/stratum)
crates: the Noise handshake and the encrypted transport, the common and
mining messages, and the server-side mining channels of `channels_sv2`.
A static library and a header, `libsv2_sri.a` and `sv2_sri.h`.

Unlike the Python and C++ bindings, these are not generated from the
UniFFI crate at the root of the repository: UniFFI has no C target. This
directory is a crate of its own, written for C, with its header generated
by cbindgen. It builds and tests on its own, with its own `Cargo.lock`.

## Why

A program written in C wants to speak Stratum V2 without writing its own
implementation of it, with SRI's code deciding what the protocol allows.
The C++ bindings need C++20, so a C program cannot use them, and the old
`sv2_ffi` crate was deprecated.

The first such program is [DATUM Gateway](https://github.com/OCEAN-xyz/datum_gateway),
which is plain C. OCEAN's plan for Stratum V2 in the gateway asks for a C
library built and released by SRI from its Rust crates. The options were
discussed in [stratum#2131](https://github.com/stratum-mining/stratum/discussions/2131);
this is the raw FFI one.

## Layout

The modules follow the UniFFI crate's (`codec`, `messages`, `channels`) and
stay inside the API boundary proposed in stratum#2131 (no `handlers_sv2`):

| Module | What it is | SRI code underneath |
|--------|------------|---------------------|
| `src/codec.rs` | One Noise session per connection: the handshake as responder (and as initiator, for tests and clients) and the encrypted transport | `codec_sv2` (`Handshake`, `NoiseEncoder`, `NoiseDecoder`) over `noise_sv2` |
| `src/messages.rs` | The 5 common and 18 mining messages as plain C records, with one decoder and one encoder | `parsers_sv2` decides what a frame holds, the channel_msg bit and the TLV rules; the structs of `common_messages_sv2` and `mining_sv2` |
| `src/frame.rs` | Frame headers | `framing_sv2` |
| `src/keys.rs` | The authority key and its base58check text form | `secp256k1`, `key-utils` |
| `src/channels/` | Server channels: an extranonce allocator, extended and standard channels that take each job as the bytes the server sends and validate the shares | `channels_sv2` (`ExtranonceAllocator`, `ExtendedChannel`, `StandardChannel`, `PrebuiltJob`) |
| `src/util.rs` | Random bytes and SHA-256 | `rand`, `secp256k1::hashes` |
| `include/sv2_sri.h` | The header, generated by cbindgen and committed | |

The SRI crates are the ones released on crates.io with
[stratum v1.13.0](https://github.com/stratum-mining/stratum/releases/tag/v1.13.0)
(`channels_sv2` 9, `mining_sv2` 13, `common_messages_sv2` 10, `parsers_sv2`
0.7, `codec_sv2` 8, `binary_sv2` 8, `framing_sv2` 9, `noise_sv2` 2.1), with
no patches on top. That release has everything the channels need
([#2445](https://github.com/stratum-mining/stratum/pull/2445),
[#2452](https://github.com/stratum-mining/stratum/pull/2452),
[#2455](https://github.com/stratum-mining/stratum/pull/2455),
[#2456](https://github.com/stratum-mining/stratum/pull/2456)). `Cargo.lock`
has `codec_sv2` 8.1.0, released the day after
([#2483](https://github.com/stratum-mining/stratum/pull/2483)).

## Building

Needs a Rust toolchain, 1.75 or newer like the SRI crates, and, the first
time, network access to crates.io. The committed `Cargo.lock` is resolved
for 1.75 and CI tests it there; `.cargo/config.toml` keeps `cargo update`
on versions that build with it.

    ./build.sh [prefix]          # default: build/

installs `lib/libsv2_sri.a`, `include/sv2_sri.h` and
`lib/pkgconfig/sv2_sri.pc` (with the system libraries the archive needs),
so a C build only needs:

    cc ... $(PKG_CONFIG_PATH=<prefix>/lib/pkgconfig pkg-config --cflags --libs sv2_sri)

When cbindgen is installed, `build.sh` fails if the committed header does
not match the sources. Regenerate it with:

    cbindgen --config cbindgen.toml --crate sv2_sri --output include/sv2_sri.h .

On x86_64, build for the CPU it will run on (`RUSTFLAGS="-C target-cpu=native"`
or `x86-64-v3`): the ChaCha20-Poly1305 of the crates costs three to four
times as much per short message on baseline x86-64.

## The API

45 functions. The rules that hold for every one of them:

- **Buffers belong to the caller.** An encoder writes into a buffer of a
  given capacity; a decoder reads the caller's payload, and the byte fields
  of the record it returns (`Sv2SriBytes`, a pointer and a length) point
  into that payload. Nothing keeps a pointer the caller passed in after
  returning. So no Rust lifetime reaches C, and the transport costs one
  copy and one allocation per frame in each direction.
- **Objects.** The only Rust allocations a caller holds are the objects of
  the `_new()` functions, each released by its `_free()`: a Noise session
  per connection, an extranonce allocator, and a channel object per channel,
  which keeps the jobs it is given.
- **Return values.** `SV2_SRI_OK` (0), a byte count where documented,
  `SV2_SRI_NEED_MORE` from `sv2_sri_noise_read_frame()`, or a negative
  `SV2_SRI_ERR_*` code. The channel codes (`SV2_SRI_ERR_CH_*`,
  `SV2_SRI_ERR_SHARE_*`) each name a crate error, and
  `sv2_sri_channel_error_code()` gives the spec's error-code string for it,
  the one to put in `OpenMiningChannel.Error`, `UpdateChannel.Error` or
  `SubmitShares.Error`.
- **No panic reaches C.** Every function runs under `catch_unwind` and
  reports a panic as `SV2_SRI_ERR_INTERNAL` (NULL from a constructor). The
  object the call was made on must then be freed, not used again; anything
  else the caller holds is fine. A server drops one connection instead of
  stopping with all of them.
- **Unknown messages are not errors.** A well-formed frame of a message or
  extension this API has no record for (template distribution, job
  declaration, an extension's messages) is `SV2_SRI_ERR_UNSUPPORTED`, and
  the caller decides whether to ignore it. TLV fields after a message are
  accepted and ignored, as `parsers_sv2` does; anything else is
  `SV2_SRI_ERR_TRAILING`.

| Group | Functions |
|-------|-----------|
| Authority key | `sv2_sri_authority_keypair_generate`, `sv2_sri_authority_pubkey`, `sv2_sri_authority_pubkey_to_base58`, `sv2_sri_authority_pubkey_from_base58` |
| Handshake | `sv2_sri_noise_responder_new`, `sv2_sri_noise_initiator_new`, `sv2_sri_noise_free`, `sv2_sri_noise_initiator_step0`, `sv2_sri_noise_responder_step1`, `sv2_sri_noise_initiator_step2`, `sv2_sri_noise_is_transport`, `sv2_sri_noise_is_authenticated` |
| Transport | `sv2_sri_noise_encrypt_frame`, `sv2_sri_noise_read_frame`, `sv2_sri_noise_encrypted_frame_size`, `sv2_sri_noise_encrypted_payload_size` |
| Framing | `sv2_sri_frame_header_decode`, `sv2_sri_frame_header_encode`, `sv2_sri_msg_has_channel_bit` |
| Messages | `sv2_sri_message_decode`, `sv2_sri_message_encode`, and the `Sv2SriMessage` record: a message type and a union of the records of SetupConnection, .Success, .Error, ChannelEndpointChanged, Reconnect, Open{Standard,Extended}MiningChannel and .Success, OpenMiningChannel.Error, UpdateChannel, .Error, CloseChannel, SetExtranoncePrefix, SetTarget, SetGroupChannel, NewMiningJob, NewExtendedMiningJob, SetNewPrevHash, SubmitShares{Standard,Extended}, .Success, .Error |
| Channels | `sv2_sri_extranonce_allocator_new/free/rollable_size`; for each of `extended_channel` and `standard_channel`: `_new`, `_free`, `_extranonce_prefix`, `_set_target`, `_update`, `_prebuilt_job`, `_job_target`, `_activate_job`, `_validate_share`; `sv2_sri_channel_error_code` |
| Utility | `sv2_sri_random`, `sv2_sri_sha256` |

Each function is documented in `sv2_sri.h`. [`tests/capi_test.c`](tests/capi_test.c)
is a short example of all of them from C: a handshake, a frame each way,
and a channel that takes a job and checks shares.

## Testing

    ./test.sh [prefix]                 # build.sh, cargo test, then tests/capi_test.c
    SANITIZE=1 ./test.sh               # the C test under ASan and UBSan
    cargo +nightly fuzz run message_decode -- -max_total_time=600

- `cargo test`: the records round trip through the encoder and the decoder,
  the transport across chunk boundaries, the channel rules with a
  hand-built coinbase, and random and mutated frames that must never
  panic.
- `tests/capi_test.c`: a C program that links only the library, and runs
  the API the way a server and a miner do, with the error paths.
- [`fuzz/`](fuzz/): cargo-fuzz targets on the C API. `message_decode` (any
  header and payload, then a re-encode round trip), `noise_transport` (any
  act 1; any stream, or frames chosen by the input and encrypted by a real
  initiator, read back in pieces chosen by the input) and `channel_share`
  (targets, UpdateChannel, jobs, SetNewPrevHash and shares in any order, on
  both channel types). A panic is a crash there: cargo fuzz builds with
  `panic=abort`, so `catch_unwind` cannot hide it.

## Status and open questions

It runs the SV2 server of a DATUM Gateway on mainnet, pooled to OCEAN. In
13.7 hours on 23 and 24 November 2026 the pool accepted 2,518 shares and
rejected none, from two Bitaxes on extended channels and a Braiins OS+
machine on a standard channel. Before that the same server ran against
SRI's own Translator Proxy and mining device.

That gateway was built on stratum
[`7b85f90`](https://github.com/stratum-mining/stratum/commit/7b85f90ca0ae6990a8eab35f00dbc468f83a8145),
two pull requests before v1.13.0. The crates this one builds on now differ
from it in three ways:

- `binary_sv2` no longer serializes a `nominal_hash_rate` that is negative
  or not finite ([#2436](https://github.com/stratum-mining/stratum/pull/2436)),
  so `sv2_sri_message_encode()` returns `SV2_SRI_ERR_INVALID` for one;
- a coinbase the crates build from a template only gets a witness when it
  has a witness commitment ([#2457](https://github.com/stratum-mining/stratum/pull/2457));
  the prebuilt jobs of this API are used as given, so nothing changes here;
- `codec_sv2` 8.1.0 encrypts a frame in place
  ([#2483](https://github.com/stratum-mining/stratum/pull/2483)), behind the
  same `encode_transport()`.

The tests, the sanitizer run and the fuzz targets pass on these crates. The
mainnet run has not been repeated on them yet.

What it does not do yet, and what is still open:

- **Server side only.** No client channels, no group channels, and no
  records for template distribution, job declaration or the extensions.
  What a first version should cover is for stratum#2131 to decide.
- **Records shaped by their first user.** The records mirror the structs of
  the C implementation they replaced in DATUM's SV2 server, field for
  field, and so do the error code values. The message records still have
  the field names from before the spec cleanup, `maximum_target` and
  `min_ntime`, where `mining_sv2` 13 says `max_target`, `target` and
  `ntime_start` (the channel records already use the new names). Happy to
  change all of it.
- **Frame headers.** stratum#2131 keeps `framing_sv2` out of an FFI. Here a
  caller reads its own socket, so the 6 byte header is in the API: a plain
  record and three functions, nothing else of that crate.
- **Names.** The prefix is `sv2_sri_` and the library `sv2_sri`; a name
  under stratum-mining would probably be different.
- **Where it lives.** Here, next to the UniFFI crate, is one choice.
  stratum#2131 also named a repository of its own (`sv2-ffi`) and a crate
  in the stratum workspace, which each release would have to keep current.
- **Two sets of crate versions.** This crate is on the crates of stratum
  v1.13.0, the UniFFI crate on those of May 2026 (`channels_sv2` 5.0.0):
  the C API needs `PrebuiltJob`, which came with `channels_sv2` 9.0.0. The
  two lock files are separate, so neither holds the other back.
- **The responder's certificate.** As in `noise_sv2`, a responder signs a
  new certificate at every handshake.
  [stratum#2437](https://github.com/stratum-mining/stratum/issues/2437)
  asks for a pre-issued one, and `sv2_sri_noise_responder_new()` changes
  with it.
- **Following the releases.** The records are written against the message
  structs of one release, so a new major version of `mining_sv2` or
  `common_messages_sv2` means updating `src/messages.rs` with it. Nothing
  this crate calls is waiting for a release: what stratum main has on top
  of these crates is `parsers_sv2` 0.8.0, three fixes to its TLV frame
  helpers, which are not used here.
